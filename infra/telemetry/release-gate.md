# Spec 27 release gate — the record, the evidence, and what changes each item

Written by Unit 27.11 on 2026-10-18. This is the record spec 27 §15 asks for **before any live provider is configured**: every item is `PASS`, `BLOCKED` or `NOT VERIFIED`, with the evidence for it and what would change it. `lib/telemetry-runbook.test.ts` holds §1 and §4 to the spec's own checklist and scenario table (every row, in the spec's words, with a valid status), so neither can quietly lose a row.

**The rule.** A `BLOCKED` or `NOT VERIFIED` item prohibits enabling the part of the feature it covers. If the choice is between losing optional analytics and paying, lose the analytics.

**Where Spec 27 stands.** Built and verified: 27.1 (settings and gates), 27.2 (consent), 27.3 (PostHog sender and events), 27.5 and 27.6 (Grafana metrics, traces, sanitized logs), 27.7 (health endpoints) and 27.10 (the Admin System tab and Analytics link). **Not built:** 27.4 (PostHog dashboards) and 27.8 (Grafana dashboards and email alerts) need live accounts and are yours to create; 27.9 (monthly SLO reporting) waits on a check of Grafana Free's API. **Nothing is on:** no PostHog or Grafana account exists, `.env.local` sets no telemetry variable, the production Vercel project has not been created yet (progress tracker, Infrastructure Status), and every run so far delivered only to local receivers.

A safe order, each step reversible by switching its variable off and redeploying:

1. **Decide, with no account:** item 4 (Hobby eligibility) and the `/privacy` wording. Neither costs anything, and the second gates PostHog.
2. **Grafana first.** Create the Free stack; add the Synthetic Monitoring check on `/api/health` (it needs no variable, so it is the safest first step); then set the Grafana variables with metrics and traces on, prove delivery (runbook §12 step 6), then logs.
3. **Dashboards and alerts (27.8), then a real test email.** An alert is not working until you have received a triggered and a resolved email.
4. **PostHog next:** create the project, set the `POSTHOG_*` variables, switch on your own account in Settings → Privacy, finish a lesson, and look for the events (runbook §11).
5. **Set the two link variables** so the Admin console links to what you built.
6. **After a week**, record each provider's usage page under item 6, and the Vercel usage page under item 8.

**To PostHog** — only for a learner who has accepted in Settings → Privacy, only from the server, only after the learner's response has been sent.

Not their name, email, Clerk id or Polyglot id; deleted with the account                                                                         | `user_analytics_consent.analytics_id`; tests assert it derives from no identifier           |
| When                       | A timestamp, and a UUID derived from the pseudonym and the event's dedupe key                                                                                                                               | `deterministicEventUuid`                                                                    |
| Properties common to all   | `language` (a code such as `es-MX`), `app_environment`, `event_schema_version`, `source` (`server` or `browser_intent`)                                                                                     | the catalog's common schema                                                                 |
| Properties of some         | A random `session_key`; `item_count` (1–100); `accuracy_percent` (0–100); `level`; `content_type` (vocabulary or grammar); `result` (advanced or penalized); the SRS stage as a band, never the exact stage | per-event strict schemas: every value is a bounded number, an enum or a UUID — no free text |
| The envelope PostHog needs | `distinct_id`, `$process_person_profile: false`, `$geoip_disable: true`, `$lib`, and the public project token as `api_key`                                                                                  | the adapter, `providers/analytics/posthog.ts`                                               |

PostHog also sees the network address of your server's request, as any HTTP server does. Turn on **Discard client IP data** in the project (runbook §11). The browser never contacts PostHog: no script, no cookie, no SDK.

**To Grafana Cloud** — only the signals you switch on, directly from the application to Grafana's OTLP gateway.

| Signal   | What is in it                                                                                                                                                                                                                             | Enforced by                                                                                    |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Metrics  | Eight counters and histograms (runbook §12) carrying only `environment`, `method`, a route template cut to three segments (`/items/:param`), `status_class`, `outcome`, an error category, `operation`, `provider` or `signal`            | the instruments' label sets, enforced again as SDK views and by the exporter guard             |
| Traces   | For 5% of requests: the request (`GET /route-template`, method, template, status class) and the application's own operation spans (`review.submission`, `review.commit`, `lesson.completion`) with outcome, error category and request id | the sampler, the span sanitizer (rebuilds every span from an allowlist) and the exporter guard |
| Logs     | Warnings and worse only: a dotted event name and a few validated attributes (operation, a fixed reason, an error code or class, a status, a duration, two ids). No message, stack, user id, email or SQL has a field to go in             | the log projection (a shape validator per field: a value that fails is dropped, not masked)    |
| Resource | `service.name`, `service.version` (the release), `deployment.environment.name`, and `service.instance.id` (a random UUID per server instance)                                                                                             | `providers/observability/start.ts`                                                             |

**Measured on a real server** (§3, with everything on and a learner opted in). The 16 PostHog events carried only catalog properties, under one random pseudonym. The Grafana posts carried exactly these span attributes: `http.request.method`, `http.response.status_code`, `http.route`, `polyglot.operation`, `polyglot.outcome`, `polyglot.trace_id`; these log attributes: `event.name`, `polyglot.duration_ms`, `polyglot.error_code`, `polyglot.operation`, `polyglot.reason`, `polyglot.request_id`, `polyglot.route`, `polyglot.trace_id`; and these four resource attributes: `deployment.environment.name`, `service.instance.id`, `service.name`, `service.version`. Nothing else.

**What never leaves, in either:** URLs and query strings, user, session or item ids, emails, names, answers, vocabulary or grammar content, notes, journal text, SQL, error messages, stack traces, headers, cookies, credentials.

**Third parties that already existed and that Spec 27 did not change:** Clerk (sign-in; its SDK reports its own usage to Clerk on **development** instances only, as its notice in the dev log says), Neon, AWS (curriculum imports), Upstash. The browser's requests are listed in §3.

## 6. Quota arithmetic

All figures are for one server instance unless stated. Grafana converts OpenTelemetry names to Prometheus names, so a counter label set is **1 series** and a histogram label set is **13** (ten bucket boundaries, `+Inf`, the sum and the count).

| Figure            | Series per instance | How it is counted                                                                                                                                                                                                                                                             |
| ----------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Absolute ceiling  | about 4,200         | The request counter at every route label (48 countable of the app's 50 templates) × 8 methods × 6 status classes (2,304), and the latency histogram at every page label × 3 operations plus the 3 API labels (1,794), plus 128 for everything else. Not reachable in practice |
| Realistic ceiling | about 1,700         | Every page served both as a page and as an action with the four status classes (388 for the counter), 1,209 for the latency histogram, 128 for the rest                                                                                                                       |
| Measured          | 813                 | One server instance through the whole browser test tour: 54 latency label sets (702 series), 70 request label sets, and 41 more                                                                                                                                               |

At the realistic ceiling 10,000 holds about five instances alive in the same window, and at the measured figure about twelve; a beta rarely has more than a few. If it nears the limit Grafana drops what it cannot take and the account stays Free. The levers are `TELEMETRY_METRICS_ENABLED=false`, or a change to the catalog (a code change).

**PostHog.** Seven events, mostly `review_item_completed`, one per item reviewed by a consenting learner. About 3,000 events a month for a learner who does 100 reviews a day, so 1,000,000 free events cover roughly 300 such learners, fewer once lessons are counted. Events over the allowance are dropped, not billed. There is no sampling setting yet; the levers are switching PostHog off or changing the catalog (a code change).

**Grafana logs and traces.** Warnings only, each well under 2 KiB, and 5% of requests as traces. In the telemetry-on run every request was traced (100% sampling), and the whole run — 3,755 spans, 21 log records and 25 metric exports — came to 3.98 MB: about 1 KB per request. At 5% sampling, a million requests a month is on the order of 50 MB of traces. Against 50 GB a month each, neither is a constraint.

**Retention.** Grafana Cloud Free keeps telemetry for 14 days, so no Grafana dashboard can prove a 28–31 day month: monthly SLO reporting is Unit 27.9, it is not built, and until it is every monthly figure is reported as incomplete rather than imputed (spec §9.4). PostHog Free keeps events for a year; withdrawing consent does not delete what was already sent, and the manual erasure steps are runbook §10. Neither retention figure has been confirmed on a live account (item 6).

**Synthetic Monitoring.** One 5-minute check from one location is about 8,928 executions a month, 9% of the 100,000 included.

**Vercel Hobby.** Telemetry adds no function invocations and no cron: it runs inside the request that produced it, after the response, and waiting on the network is not CPU time. The Admin links and System tab add no request to either vendor.
