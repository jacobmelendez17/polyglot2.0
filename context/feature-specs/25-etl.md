# Admin Curriculum Operations & CSV Pipeline

## 1. Purpose

Polyglot's Admin curriculum workflow should be redesigned around a **CSV-first curriculum operations pipeline**.

The goal is to remove unnecessary manual administrative work while preserving:

- stable curriculum identity
- existing learner progress
- SRS state
- review history
- deck membership
- publication safety
- audit history
- existing domain boundaries

Administrators should primarily use CSV to:

- create curriculum
- create Levels
- create vocabulary groups/themes
- create vocabulary and grammar items
- update existing curriculum
- add new metadata fields in bulk
- reorganize curriculum
- validate curriculum
- correct import problems
- enrich curriculum metadata

Admin should primarily be used to:

- review imported changes
- resolve exceptional conflicts
- write learner-facing definitions/explanations
- write and manage example sentences
- review validation warnings
- explicitly publish curriculum changes
- perform exceptional manual edits

The intended workflow is:

```text
CSV
  ↓
Upload
  ↓
Parse + Normalize
  ↓
Resolve Curriculum Identity
  ↓
Resolve/Create Level + Batch Structure
  ↓
Validate Columns + Data
  ↓
Spellcheck
  ↓
Metadata Enrichment
  ↓
Compare Against Current Curriculum
  ↓
Review / Repair Conflicts
  ↓
Confirm Import
  ↓
Commit Draft/Pending Changes
  ↓
Optional Bulk Publish
```

The existing CSV/Lambda import pipeline should be extended rather than replaced by a parallel import system.

---

# 2. Source of Truth

Neon/PostgreSQL remains the authoritative curriculum database.

CSV is an **authoring and bulk-maintenance format**, not the live runtime database.

A CSV may propose changes to curriculum state, but an uploaded file must never automatically become learner-visible curriculum merely because it was uploaded.

There will be no Google Sheets synchronization in this scope.

There will be no second curriculum database.

---

# 3. Curriculum Identity

Every official curriculum entity must have a stable external curriculum key.

This includes:

- Levels
- vocabulary groups/themes
- vocabulary items
- grammar items
- future curriculum item types where appropriate

The existing internal UUID/database identity remains authoritative internally.

The curriculum key exists so administrators and imports can safely identify the same curriculum object over time.

## 3.1 Immutable Keys

A curriculum key must never depend on mutable curriculum placement.

For example:

```text
es-MX:vocab:k7p4m2
es-MX:grammar:f3q9x1
es-MX:level:a1b7c4
es-MX:group:m8d2p5
```

The suffix is generated by Polyglot.

Admins do not manually invent keys.

Keys must be:

- globally unique within Polyglot
- immutable
- language-scoped in their readable prefix
- item-type aware
- safe for CSV usage
- indexed
- never recycled after archival

Changing an item's Level, batch, group, translation, spelling, or curriculum order must **not** change its curriculum key.

## 3.2 Curriculum Path

Placement is represented separately through a derived curriculum path.

Example:

```text
es-MX:L01:B02:vocabulary
```

If the item later moves to:

```text
es-MX:L02:B01:vocabulary
```

its curriculum path changes.

Its curriculum key does not.

This gives administrators both:

- permanent identity
- human-readable current placement

## 3.3 New Items

A new CSV row may leave `curriculum_key` blank.

During import Polyglot generates a proposed curriculum key.

After successful creation, that key becomes permanent.

The Admin import results must allow the administrator to download an updated canonical CSV containing the newly assigned keys.

All later bulk maintenance should preferably use those keys.

---

# 4. Existing Level 1 Migration

Level 1 is already published and may already have learner progress attached to its items.

The redesign must therefore migrate Level 1 **in place**.

No Level 1 learning item may be deleted and recreated merely to adopt the new Admin system.

The migration must:

1. Add curriculum-key support additively.
2. Backfill a curriculum key onto the existing Level 1 record.
3. Backfill keys onto its existing vocabulary groups.
4. Backfill keys onto every existing Level 1 vocabulary and grammar item.
5. Preserve every existing `learning_item` ID.
6. Preserve all learner progress.
7. Preserve SRS state.
8. Preserve review history.
9. Preserve deck membership.
10. Preserve user notes and user synonyms.
11. Preserve publication state.
12. Generate a new canonical Level 1 CSV containing the keys and expanded schema.

Any new metadata/enrichment capability introduced by this spec must also be available to Level 1.

Level 1 must not become a legacy exception to the new pipeline.

## 4.1 Level 1 Metadata Upgrade

After key backfill, Level 1 can run through the same pipeline used for later curriculum.

For example, the pipeline may identify missing:

```text
pronunciation
IPA
synonyms
variations
part of speech
article
other supported metadata
```

Proposed changes to already-published learner-facing content should enter the normal draft/review process.

Internal key backfills do not require learner-facing publication.

## 4.2 Migration Verification

Tests must prove that before and after the Level 1 migration:

```text
learning_item.id remains unchanged
user_item_progress still references the same items
review history remains attached
deck membership remains attached
published item counts remain correct
Level 1 remains accessible
Demo Level 1 remains functional
```

# 5. Canonical CSV Schema

Polyglot should have one canonical curriculum CSV format capable of containing both vocabulary and grammar.

Example:

```csv
curriculum_key,language,item_type,word,translation,level,level_name,batch_number,batch_name,pronunciation,ipa,synonyms,variations,article,part_of_speech,context,tags
,es-MX,vocabulary,gato,cat,2,Core Foundations,1,Core Vocabulary,GAH-toh,ˈɡato,feline|kitty,gatito,el,noun,,
,es-MX,grammar,pero,but,2,Core Foundations,5,Grammar,,,,,,,,,
```

## 5.1 Core Columns

The canonical schema supports at least:

```text
curriculum_key
language
item_type
word
translation
level
level_name
batch_number
batch_name
pronunciation
ipa
synonyms
variations
article
part_of_speech
context
tags
```

Vocabulary and grammar share one file.

`item_type` determines which fields are applicable.

## 5.2 Required Import Identity

A new item must minimally provide enough information to establish:

```text
language
item_type
word
translation
level
batch_number
```

`level_name` and `batch_name` are required when the corresponding Level/group does not already exist.

A row targeting existing structure does not need to redefine names every time.

## 5.3 Expected Vocabulary Metadata

Vocabulary supports:

```text
word
translation
pronunciation
IPA
synonyms
variations
article
part of speech
context
```

The columns should exist in the canonical format even if the pipeline initially fills some of them.

Missing enrichable metadata should not force the administrator to type it manually.

## 5.4 Grammar Rows

Grammar uses the same CSV.

Vocabulary-only fields may be blank or `N/A`.

A grammar row must never create a fake vocabulary group merely because it has a batch number.

`batch_number` may still express its authored curriculum placement/order.

Grammar-specific fields can be added to the canonical schema as the existing grammar domain requires them.

---

# 6. Manual-Owned Content

The administrator's primary manual curriculum-writing responsibility should be:

```text
learner-facing definition / explanation
example sentences
example-sentence translations
```

These fields are **manual-authority fields**.

Ordinary CSV re-import must not overwrite them.

Dictionary enrichment must not silently overwrite them.

A learner-facing explanation is not interchangeable with a dictionary gloss.

Admin should clearly distinguish:

```text
machine/imported metadata
dictionary/reference metadata
manually authored teaching content
```

---

# 7. Patch Imports

The same CSV pipeline must support both creation and patching.

Separate "create importer" and "update importer" systems should not exist.

The resolver decides what each row means.

Each row resolves to:

```text
create
update
move
unchanged
blocked
```

## 7.1 Column-Level Patching

Only fields actually supplied by an import may be modified.

Example:

```csv
curriculum_key,ipa
es-MX:vocab:k7p4m2,ˈɡato
es-MX:vocab:p8q1d5,ˈpero
```

This import may update IPA.

It may not alter:

```text
translation
level
batch
synonyms
examples
definition
anything else
```

This is the primary workflow for adding a new metadata column to an already-published Level.

## 7.2 Omitted Columns

An omitted CSV column means:

> Do not modify this field.

## 7.3 Blank Cells

A blank cell means by default:

> Do not modify the existing value.

Blank cells must never accidentally erase existing curriculum.

## 7.4 Explicit Clearing

Clearing existing content must require an explicit value such as:

```text
__CLEAR__
```

The preview must make the deletion obvious before confirmation.

## 7.5 Changed Fields Only

If a full curriculum CSV is uploaded, Polyglot compares the supplied values to current curriculum.

Only actual differences are proposed.

Example:

```text
word             unchanged
translation      unchanged
level            unchanged
batch            unchanged
IPA              changed
synonyms         unchanged
```

The row therefore becomes an IPA-only update.

## 7.6 Column Selection

Before confirmation, Admin should show all changed columns and allow the administrator to exclude an unintended column from that import.

This protects against accidental spreadsheet edits.

---

# 8. Multi-Value Columns

Fields such as:

```text
synonyms
variations
tags
accepted meanings
```

should use a consistent human-editable format.

Recommended canonical representation:

```text
term one|term two|term three
```

The parser must:

- trim whitespace
- remove exact duplicates
- preserve meaningful accents
- preserve ordering where meaningful
- validate invalid entries

A supplied nonblank list replaces the official value for that imported field unless that field is protected by a manual override.

Learner-specific synonyms are separate and must never be replaced by curriculum imports.

---

# 9. Automatic Level and Group Creation

Admins should not need to manually create empty Levels and groups before importing curriculum.

If the CSV contains:

```text
level = 3
level_name = Everyday Life
batch_number = 2
batch_name = Food & Drinks
```

and that structure does not exist, preview may propose:

```text
CREATE LEVEL 3 — Everyday Life
CREATE GROUP 2 — Food & Drinks
CREATE ITEM ...
```

The administrator confirms the complete import rather than manually creating each dependency beforehand.

## 9.1 Existing Structure

Existing Levels/groups should be reused.

The importer must never silently rename an existing Level/group because an uploaded file contains a different name.

Instead:

```text
Existing:
Level 3 / Batch 2 = Food

CSV:
Level 3 / Batch 2 = Food & Drinks
```

becomes a reviewable conflict.

The administrator can:

```text
keep existing name
rename structure
correct staged CSV value
skip affected change
```

The resolver then runs again.

---

# 10. Import Conflict Repair

Import review must become a **repair workflow**, not a skip workflow.

A blocked row must explain exactly why it is blocked.

Examples:

```text
Unknown curriculum key
Duplicate candidate
Ambiguous existing item
Invalid Level
Invalid batch
Conflicting group name
Invalid item type
Malformed IPA
Invalid column value
Structural move requires approval
Spellcheck warning
Existing data changed since preview
```

## 10.1 Available Resolution Actions

Depending on conflict type, Admin may:

```text
Edit staged row
Select an existing curriculum item
Assign the correct curriculum key
Correct Level
Correct batch
Correct group name
Accept a spellcheck suggestion
Approve a structural move
Explicitly create a legitimate separate homonym
Keep existing database value
Skip the row
```

Skip remains available but is no longer the only way forward.

## 10.2 Immediate Revalidation

After every repair:

```text
admin changes value
       ↓
normalize
       ↓
validate
       ↓
resolveImportRow
       ↓
reclassify
```

For example:

```text
BLOCKED
Invalid batch 8
```

Admin changes:

```text
8 → 3
```

Polyglot immediately reruns the resolver.

The row may become:

```text
MOVE
Level 2 / Batch 1 → Level 2 / Batch 3
```

The administrator then approves the move.

No new CSV upload is required.

## 10.3 Structural Move Approval

Changing Level or batch on an existing item is considered a structural change.

It must never happen silently.

Preview displays:

```text
MOVE

gato
Level 1 / Batch 3
→
Level 2 / Batch 1
```

Admin explicitly selects:

```text
Approve Move
```

Once approved, the row is resolved.

Moving the item must preserve its curriculum key and internal learning-item ID.

## 10.4 Fresh Resolution at Commit

Preview is not authoritative.

Immediately before commit, Polyglot reruns resolution against current database state.

If the curriculum changed after preview, the affected row returns to review rather than silently overwriting newer data.

---

# 11. Corrected CSV Export

If an administrator fixes import data inside Admin, Polyglot should offer:

```text
Download Corrected CSV
```

This export contains:

- generated curriculum keys
- accepted inline corrections
- corrected structure
- normalized list formatting

This prevents the administrator's external source file from repeatedly producing the same conflict.

---

# 12. Spellcheck and Language Validation

Spellchecking is advisory.

It must never silently rewrite official curriculum.

For Spanish:

- preserve accents
- preserve ñ
- preserve meaningful punctuation
- treat Mexican/Latin-American Spanish as the intended language context
- do not treat accent differences as interchangeable

For example:

```text
si
sí
```

remain distinct.

A suspected spelling problem produces:

```text
Warning
Suggested correction: ...
```

Admin may:

```text
Accept suggestion
Keep original
Edit manually
```

Any change reruns row validation.

English translations may receive similar spelling warnings.

---

# 13. Metadata Enrichment

The import pipeline should automate safe metadata wherever the existing dictionary/lexicon architecture can provide reliable information.

Potential enrichable fields include:

```text
part of speech
IPA
pronunciation metadata
variants
synonyms
article validation
regional evidence
canonical lemma
```

Enrichment is evidence, not unrestricted authorship.

The pipeline must not automatically generate official learner-facing teaching explanations or example sentences.

## 13.1 Provenance

Automated fields should expose where the value came from when useful:

```text
CSV
Dictionary
Lexicon
Admin
System
```

Admin should be able to understand why a value exists.

## 13.2 Manual Override Protection

If an administrator manually overrides an automatically managed metadata field, that field becomes protected.

Later enrichment must not silently overwrite the manual correction.

The UI should indicate:

```text
IPA
/ˈɡato/
Manual override
```

---

# 14. Publication Rules

Uploading a CSV does not itself publish learner-visible curriculum.

## 14.1 New Items

New imported items enter the existing pre-publication lifecycle.

Definitions and example sentences are **not required publication gates**.

Admin may publish a structurally valid item before those fields are complete.

The work queue should continue to show that the content needs additional authoring.

## 14.2 Existing Published Items

Changes to learner-facing fields on published items must use the existing draft/revision behavior.

The live published item remains available until the administrator explicitly publishes the new revision.

## 14.3 Bulk Publish Import Changes

After a successful import Admin should show:

```text
Import complete

57 rows processed
4 new items
18 updated items
2 structural moves
33 unchanged
0 unresolved

18 published items now have draft changes.

[ Review Changes ]
[ Publish All Eligible Imported Changes ]
```

The bulk publish operation must use existing publication validation and be atomic where appropriate.

The administrator should not need to open and publish 18 items individually.

Useful filters include:



Definitions/examples remain optional publication-wise but easy to find.

# 16. Manual Item Editing

Manual editing remains available for exception handling and teaching content.

The item editor should prioritize:

```text
Definition / Explanation
Examples
Creator Notes
Manual metadata overrides
```

Administrative metadata should not dominate the screen when it is normally maintained through CSV.

Provide:

```text
Save
Save & Next
Previous
Next
Next Incomplete Item
Return to Results
```

This allows rapid definition/example authoring.

---

# 17. Admin Navigation Improvements

Admin navigation state must survive normal navigation.

List state should be represented in URL/search parameters where practical.

Persist:

```text
search
language
level
batch/group
item type
status
work-queue filter
sort
cursor/page
```

Example:

```text
/admin/curriculum?language=es-MX&level=2&type=vocabulary&needs=definition
```

Opening an item and pressing Back should restore:

- the same filter
- the same sorting
- the same page/cursor
- the same result context
- the previous scroll position where practical

Admin item pages should provide:

```text
Curriculum > Spanish > Level 2 > Food & Drinks > gato
```

and:

```text
← Return to Results
```

Unsaved manual edits require a navigation warning.

---

# 18. Saved Admin Views

Admins may save common filter combinations.

Examples:

```text
Level 2 — Needs Definitions
Published Spanish With Warnings
Recently Imported
Needs Examples
Draft Changes
```

These are UI conveniences only.

They do not become authoritative curriculum state.

---

# 19. Export

Admin should support canonical export.

At minimum:

```text
Export Language
Export Level
Export Batch
Export Current Filter
```

Exports include curriculum keys.

This creates the recommended maintenance loop:

```text
Export existing Level
↓
Add or edit desired column
↓
Import CSV
↓
Review diff
↓
Apply
```

For a new metadata field, an administrator can therefore:

```text
Export Level 1
Add pronunciation column
Fill/derive pronunciation
Re-import
```

The importer matches by curriculum key and proposes only pronunciation differences.

---

# 20. Deletion and Missing Rows

The absence of an item from a CSV never means:

```text
delete
archive
unpublish
```

Destructive operations must always be explicit Admin actions.

This prevents an accidentally incomplete spreadsheet from removing curriculum.

---

# 21. Import State and Audit History

Every import retains an auditable record including:

```text
import ID
source filename
source checksum
actor
timestamp
environment
rows processed
created count
updated count
move count
unchanged count
skipped count
blocked count
published-after-import count
```

For repaired rows, audit history should record:

```text
original proposal
administrator correction
final resolved action
```

For structural moves:

```text
old Level/batch
new Level/batch
approving administrator
```

Do not store or log unrelated learner information.

---

# 22. Import Safety

The pipeline must remain:

- authenticated
- admin-authorized
- runtime validated
- idempotent
- auditable
- transactional where consistency requires it
- safe to retry
- safe against stale previews
- safe against duplicate commits

Import commits must continue using the shared curriculum resolver and curriculum domain logic.

The Lambda pipeline must not implement separate curriculum rules.

---

# 23. UI States

Every import screen requires designed:

```text
uploading
parsing
validating
enriching
needs review
ready
importing
completed
failed
retrying
```

states.

A long-running import must clearly communicate what is happening.

Errors must identify whether:

- nothing was written
- some review decisions remain
- the commit failed safely
- retry is available

Raw stack traces must never be shown.

# 24. Level 1 Rollout

The first real adoption of this spec should be Level 1.

Recommended rollout:

### Phase A — Identity

Add curriculum keys and backfill them onto Level 1 without changing learner-facing content.

Verify all existing IDs/progress remain intact.

### Phase B — Canonical Export

Generate the new canonical Level 1 CSV containing:

```text
curriculum keys
item types
Level metadata
batch metadata
current vocabulary/grammar
current supported metadata
```

### Phase C — Pipeline Re-import

Run the canonical Level 1 file back through the new resolver.

Expected result:

```text
unchanged
```

for all unchanged curriculum.

Any unexpected update is a blocker that must be understood before continuing.

### Phase D — Metadata Upgrade

Run missing metadata through enrichment and/or add new CSV columns.

Preview the Level 1 field-level diff.

### Phase E — Publish

Commit approved changes.

For already-published fields, create drafts.

Bulk publish the approved Level 1 revisions once reviewed.

At no point should learner progress be reset.

# 25. Recommended Implementation Units

This redesign must be implemented incrementally.

### Unit 1 — Curriculum Keys

Add stable keys to Levels, groups, and learning items.

Backfill existing curriculum, especially published Level 1.

Add indexes/constraints and migration tests.

### Unit 2 — Canonical CSV Schema

Extend parser/validation for:

```text
curriculum_key
language
item_type
level_name
batch_name
new metadata columns
```

Add mixed vocabulary/grammar parsing.

### Unit 3 — Structure Resolution

Allow imports to resolve or propose Levels/groups automatically.

Reuse existing structures safely.

### Unit 4 — Key-Based Re-import and Field Patching

Make curriculum keys the primary import match.

Implement column-presence semantics, explicit clearing, field-level diffs, and patch imports.

### Unit 5 — Conflict Repair

Replace skip-only conflict handling with staged row editing, matching, structural approval, homonym handling, and immediate revalidation.

### Unit 6 — Spellcheck and Metadata Enrichment

Integrate validation/enrichment through existing language and lexicon boundaries.

Protect manual overrides.

### Unit 7 — Publication and Import Summary

Create import-aware bulk publication and post-import summaries.

### Unit 8 — Admin Editorial Workflow

Add work queues, Save & Next, incomplete-content navigation, and optimized definition/example authoring.

### Unit 9 — Navigation State

Move Admin filters/sort/cursor into URL state and add breadcrumbs/Return to Results behavior.

### Unit 10 — Level 1 Full Migration Verification

Export, re-import, metadata-upgrade, bulk-publish, and verify Level 1 end to end with existing learner progress preserved.

# 26. Acceptance Criteria

This spec is complete when all of the following are true:

1. Every existing official Level, group, vocabulary item, and grammar item has a permanent curriculum key.
2. Published Level 1 adopts those keys without replacing learning-item IDs.
3. Existing Level 1 learner progress remains untouched.
4. One CSV can contain both vocabulary and grammar.
5. New Levels/groups can be proposed automatically from CSV.
6. CSV can create new curriculum.
7. CSV can update existing curriculum.
8. CSV can perform one-column patch updates.
9. Omitted columns never erase data.
10. Blank cells do not erase data.
11. Explicit clearing requires an explicit operation.
12. Imported rows are matched primarily by curriculum key.
13. Moves retain stable identity.
14. Structural moves require explicit approval.
15. Blocked rows can be corrected without re-uploading the file.
16. Correcting a blocked row automatically reruns validation and resolution.
17. A repaired row visibly changes classification when the repair succeeds.
18. Skip remains available but is never the only conflict-resolution mechanism.
19. Spellcheck does not silently modify content.
20. Existing database changes since preview are detected before commit.
21. Definitions/examples are not required publication gates.
22. Definitions/examples remain easy to find through work queues.
23. Existing published content receives draft changes rather than silent learner-facing overwrites.
24. Imported draft changes can be bulk published.
25. Admin filters and navigation survive item editing/back navigation.
26. Current curriculum can be exported with curriculum keys.
27. Inline import corrections can be exported as a corrected canonical CSV.
28. Import history remains auditable.
29. Duplicate protection continues to work.
30. No import operation can reset learner progress implicitly.

---

# 27. Non-Goals

This spec does not introduce:

- Google Sheets synchronization
- bidirectional external database synchronization
- AI-generated official definitions
- AI-generated official example sentences
- automatic deletion because a CSV row disappeared
- silent publication
- replacement of Neon as the source of truth
- a second curriculum domain
- a second import resolver
- separate vocabulary and grammar import systems
- learner progress migration to new item IDs
